ClipMux is open-source video infrastructure you run on your own accounts. Paste Cloudflare R2 credentials and a Modal API key and you get Mux-style ingestion, GPU transcoding, signed playback, and a dashboard — without a metered SaaS in the middle.

## What ClipMux Does

At a high level, ClipMux helps you:

- upload source video files (direct-to-storage multipart)
- process them into playback-ready HLS/DASH outputs
- serve those outputs through a Cloudflare delivery worker
- control access with signed or public playback rules
- integrate the experience into your own product, UI, and backend

The platform is focused on VOD first. Live streaming can come later; the current foundation is reliable video-on-demand on infrastructure you control.

## Core Concepts

### Assets

An asset is the canonical video object inside ClipMux. It begins as an uploaded source file and becomes the reference point for processing status, playback metadata, and delivery configuration.

### Processing

After ingestion, ClipMux analyzes and transcodes the source (Modal GPU pipeline: FFmpeg, Shaka, optional Whisper) into formats suitable for streaming playback.

### Playback

Once an asset is ready, ClipMux exposes a playback URL and, for private assets, a short-lived JWT. `@clipmux/player` consumes that URL.

### Delivery

Delivery is always a **Cloudflare Worker** in front of R2 (there is no Docker/Node delivery path). It verifies playback JWTs, rewrites manifests, serves byte ranges, and meters bandwidth into Analytics Engine.

## Upload and Processing

The intended workflow looks like this:

1. Your app requests an upload token from the ClipMux API.
2. The source file is uploaded to your R2 raw bucket via presigned URLs.
3. The Modal pipeline prepares adaptive-bitrate output in your transcoded bucket.
4. Your backend or frontend retrieves playback details when the asset is ready.

This model works for dashboard-driven workflows and fully custom product flows where your application owns the UI and business logic.

## Playback and Delivery

Playback is designed around the same concerns as larger platforms:

- fast startup time
- adaptive delivery
- controlled access (signed JWTs with UA/domain binding)
- predictable URLs and playback identifiers
- a drop-in React player (`@clipmux/player`)

The delivery worker is Cloudflare-only and that is **fixed**, not a default. The API and dashboard can run on Node or Docker; signed playback still goes through the delivery worker in front of R2. See [Deployment](/deploy).

## Deployment Shapes

An installation chooses part of its infrastructure and inherits the rest:

| Axis | Options | Selected by |
| --- | --- | --- |
| Postgres | bundled/dev Postgres \| any `postgresql://` URL | `DATABASE_URL` |
| Transcode provider | Modal GPU \| one local worker | `TRANSCODE_PROVIDER` (deployment setting) |
| Dispatch transport | direct HTTP \| QStash | `QSTASH_TOKEN` presence |
| Rate-limit store | in-memory \| Redis (TCP) \| Upstash (REST) | `REDIS_URL`, else Upstash REST, else in-memory |
| Analytics | on (default) \| off | `ANALYTICS_ENABLED`; writes go through the delivery worker |

**Fixed:** delivery is always the Cloudflare delivery worker + R2, and object storage is always Cloudflare R2. `GET /health/config` reports the resolved choices in its `deployment` object — see [the health endpoint](/api-reference#get-healthconfig) for the full shape.

## API-First by Default

The platform is shaped for developers first:

- backend services create and manage assets programmatically
- frontend apps initiate upload flows with short-lived upload tokens
- SDKs reduce ceremony around upload and playback
- webhooks fit into existing product workflows
